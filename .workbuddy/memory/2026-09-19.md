### 1. 真人现象 → 根因（先调查，未先改码）

真人录屏：Next Run Validation 跑完第一场后，**底部按钮可见，连点完全无响应**。

链路逐层落地（每一层都是「断的」）：

| # | 层 | 结论 | file:line（改前） |
|---|---|---|---|
| 1 | 按钮是否有 hit rect | **有**（`runActionButtonRect()`），但不可达 | `runPage.ts:747` |
| 2 | 当前 phase 是否允许 action | `RESULT` 在状态机里 **`runActionEnabled === true`** ⇒ 若放过去会**推进到第二场** | `runPageState.ts:424` |
| 3 | pointer/click 是否进 handler | 进了 `onPointerDown`，但在 **hit test 之前**就 `return` | `runPage.ts:744` |
| 4 | handler 是否 dispatch | **没有**（无任何 dispatch） | — |
| 5 | 动作是否有 transition | **不存在**（终点态根本没有 action） | — |
| 6 | Hub route 是否被调用 | **从未调用**（页面无导航能力） | — |

⇒ 形态 = **「有按钮但无 action」**：`actionLabelNow()` 返回的是**状态描述** `'下一局验证完成'`，
却被画在唯一主动作位置上；`actionEnabledNow()` 恒 `false`（画成禁用色）。
三层同时失效 ⇒ 点击必然被吞。

⚠️ `runActionEnabled(RESULT) === true` 是关键事实：终点态**必须继续拦截** Run 的正式流程动作
（否则一点就推进第二场），但拦截的同时**必须放行自己的出口**。

### 2. 为什么 E2E 全绿却没拦住（本 Queue 最值得记的一条）

`tests/_e2e_next_run.cjs` **把 bug 当成预期行为钉死了**：
- 旧 `N20`：`actionLabel === '下一局验证完成' && actionEnabled === false`
- 旧 `N22`：主动作强调条面积 `≈ 0`（=「按钮真的不可用」）
- 旧 `N23`：连点两次 → 状态完全不变

三条断言恰好**完整描述了 P0 的表现**，所以机器认为一切正常（47/47 PASS）。
⇒ 教训：**凡断言「禁用 / 终点」状态，必须同时断言「存在一个真实出口」**，
否则那条断言只是在给缺陷背书。（这是「tech pass ≠ 真人体验通过」的反面：**tech pass 也可能在保护缺陷**。）

### 3. 修复（最小、数据驱动，不碰冻结项）

1. **终点态身份与按钮文案分离**：`NEXT_RUN_VALIDATION_LABEL` 由状态描述 `'下一局验证完成'`
   改为**动作** `'返回验证中心'`；终点态身份交给 probe 的 `validationComplete`。
2. **文案与行为同源**：新增 `nextRunFinalAction(validationComplete, exitHref)`（纯函数）
   → `{ label, href } | null`。`RunPage` 的 `onPointerDown` / `actionLabelNow` /
   `actionEnabledNow` / `drawActionButton` **四处全部读它** ⇒ 结构上不可能再分叉。
3. **防无效按钮**：终点态若「没给 `exitHref`」或「没给 `onExit`」⇒ **一个按钮都不画**
   （而不是画一个点了没反应的）。
4. **清理 + 出口**：`requestExit()` 先 `dispose()`（停战斗循环 / 释放真实战斗运行时 /
   物理世界 / 弹丸 / 接触 / 事件订阅 / 摘监听 + 断开 RO / 清种子浮层引用），再交宿主导航。
5. ⚠️ **导航不放在 `runPage.ts`**：`RP-25` 机器禁止 `RunPage` 写 `location` / `history`
   —— 本文件与**正式玩家页面** `run-page.html` 共用，玩家页面必须结构上无法跳转。
   ⇒ 出口经 `RunPageOptions.onExit` 回调发给**宿主** `nextRunMain.ts`，
   由它 `window.location.assign(exit.href)`（整页导航，沿用 Hub 既有口径，不做路由重构）。
6. ⚠️ **返回地址放在 `nextRunValidation.ts`（`NEXT_RUN_EXIT_HREF`），不 import Hub 模块**：
   Hub 与入口是**单向**关系（Hub 认识入口，入口不认识 Hub）。

### 3b. 两处「守卫抓到真实结构问题」的返工（都在本轮真实踩到）

**返工 1｜`RP-25`**：我最初直接把 `window.location.assign` 写在 `runPage.ts` 里 ⇒
`RP-25`（Run Page 不写 `location` / `history`）立刻 FAIL。
**守卫是对的**（该文件与玩家页面共用）。改法 = 把导航移到宿主 `nextRunMain.ts`，**不放宽守卫**。

**返工 2｜`I4`（更微妙，值得记）**：我最初把返回地址定义为 Hub 数据源的两个新常量
（`VALIDATION_HUB_HREF`），由 `nextRunMain.ts` import ⇒ `validationHub.ts` 一下子变成
**跨两个入口的共享模块** ⇒ Vite 把它拆成独立共享 chunk ⇒ **Hub 页面多加载一个 chunk** ⇒
`_e2e_validation_hub.cjs` 的 `I4`（「Hub 只允许引用自己的 chunk + polyfill」）FAIL。
这不是守卫过于严格，而是**依赖方向被反转**（Hub 从「叶子页面」变成「被依赖的模块」），
与 `validationHub.ts` 头部的设计意图（入口 hub-agnostic、`VALIDATION_HUB_BACK_HINT` 就是为此存在）冲突。
⇒ 改法 = 返回地址写进**本页自己的**数据源 `nextRunValidation.ts`，两端各留一处字面量，
用 `NR-19` 做**双向交叉核对**（返回目标必须是「挂 Hub 脚本 + 入口表里真的有 next-run.html」的那一页）。
修后 `validationHub.html` 的引用回到 `[自己的 chunk, polyfill]`，I4 **零改动**恢复绿。

**结果**：`src/lab/portraitBattleLab/validationHub.ts` 与 `tests/portraitValidationHub.test.ts`
**最终零 diff** —— Queue 冻结项「Validation Hub 结构」完整成立。
