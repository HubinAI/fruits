## 事件链实测（本地 dist-pages 含临时日志，1363×936 DPR1）
- **A(681,742)**：onDown 入参 (681,742, rect 0/153/1363/629.82, clientW=844, hasToLogical=true) →
  clientToLogical → (421.69, 364.72) → handlePointer → screenToLayout 恒等(scale=1) → **HIT
  home-find-opponent(282,340,280,50)** → phase garage→matching→matchPreview。
- **B(422,518)**：clientToLogical → (261.31, 226.02) → **HIT home-vehicle（车辆气泡，非 CTA）** →
  无导航。B 命中的是车辆气泡而非战斗——与用户（B→战斗）仍不同。
- 事件段 1：pointerdown/up/click + mousedown，pointerType=mouse，offsetX/offsetY=CSS 局部
  （A=421.7/364.7；B=261.3/226.0，即浏览器已按 844 空间给 offset）。

## 根因（翻转实验决定性证实）
- **`clientToLogical` 依赖 `getBoundingClientRect()` 返回「含 transform scale 的视觉尺寸」**。
- 模拟 `transform:none`（rect 变 844×390 top=153，= 布局尺寸）后：
  A → clientToLogical(681,742, rect 844×390) → **(681, 589)** 超界 MISS 不触发 ✓用户行为；
  B → **(422, 365)** → **HIT home-find-opponent** → matching ✓用户行为。
- 机制：rect.width=844=logicalW 时公式 `(clientX-left)×844/844 = clientX` 退化为**无 X 缩放**
  （Y 只减 top）→ 即「绘制正确（CSS transform 视觉放大）、输入按布局尺寸映射」的错位。
- **playwright（现代 Chromium headless）getBoundingClientRect 含 transform（1363）→ 转换正确**；
  用户浏览器返回布局尺寸（844）→ 无缩放 → 与用户复现完全一致。差异=浏览器对 transform
  的 getBoundingClientRect 行为（或 transform 未生效），具体 UA/内核需用户提供。

## 145/145 门禁为何通过
门禁在 playwright Chromium 运行（rect 含 transform=1363），clientToLogical 正确缩放；
门禁 analyze() 的 rect 同源（1363）→ toScreen 自洽 → 点击 client 坐标正确 → 通过。
门禁从未在「rect=布局尺寸」环境运行 → 未暴露该缺陷。

## 建议最小修复（本队列未实施）
- clientToLogical 增加**不依赖 getBoundingClientRect 的路径**：用 transform 自身 s/ox/oy
  （`logicalX=(clientX-ox)/s; logicalY=(clientY-oy)/s`），rect 仅作 scale 未初始化时的 fallback；
  绘制与输入共用同一 s/ox/oy → 环境无关。
- 或 host 传 rect 前用 `viewportTransform.cssRect()`（内部 s/ox/oy）校准。
- 门禁补「rect=布局尺寸」模拟用例（transform:none）防回归。
