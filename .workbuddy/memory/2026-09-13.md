## PRP-BUILD-01-TWO-STEP-CANNON-BUILD（两层 Cannon Build：第一次选择决定第二次条件池）

### 0. 验证的核心假设
> **第一次强化会改变第二次强化的价值与期待 → 形成 Build，而不是连续拿两个互不相关的 Buff。**

流程升级为 `基础战斗 → 三选一① → 强化后战斗 → 条件池三选一② → 最终战斗 → 结束`，全程同一 Run Page。

### 1. 三条 Build 路线（第二层条件池 = 固定，不随机）

| 第一层 | 强联动 synergy | 安全通用 safe | 轻度转向 pivot |
|---|---|---|---|
| 重型弹头 | **动能爆发** kineticBurst | 紧急维修 emergencyRepair | 快速装填 fastReload |
| 双联炮 | **三连装填** tripleLoad | 紧急维修 emergencyRepair | 重型弹头 heavyShell |
| 快速装填 | **反冲蓄能** recoilCharge | 紧急维修 emergencyRepair | 双联炮 twinCannon |

⚠️ 第三格复用**第一层**的某一项 → 它的 `role` 仍是 `'base'`（`role` 描述「定义在总池里的身份」，
转向语义由**槽位**表达）。第一版不要用 `pool[2].role === 'pivot'` 做断言。

### 2. 必改 4 的接缝判定（本 Queue 最重要的调查结论）
反冲蓄能**不需要**修改任何正式模块 → **未触发停止条件**。三处干净接缝：
1. `PlanckBattleOrchestrator.onCombatEvent`（`planckBattleOrchestrator.ts:413`）是公开订阅口；
2. `WeaponFireEvent`（`cannonBehavior.ts:352`，**每次真实开火恰好一次**）与 `DamageEvent`
   （`combatEvents.ts:36`，含 `source`/`target`/`damageSource`/`behavior`/`relativeVelocity`）是正式既有事件；
3. `world.applyLinearImpulse` 是公开 API，且**正式 Cannon 自己就用它做 recoil**（`cannonBehavior.ts:363`）。

### 3. 架构：能力模块只拿**端口**，不拿编排器
两条 Lab 硬守卫逼出了更好的设计（都是真守卫，不是要绕过去）：

  新文件 `runBuildAbilities.ts` 因此**不 import 编排器**，改为声明极窄的 `RunAbilityPorts`
  （`subscribe` / `isFinished` / `facingOf` / `projectileMass` / `applyImpulse`），
  由 `RunBattleRuntime` 适配实现 → 「PRP ↔ 正式战斗栈只有 runBattleRuntime 相连」在**运行期**也成立。
  连带把 `readRunProjectileMass(orchestrator)` 放进 `runBattleRuntime.ts`。
- **G1-08（`tests/portraitBattleLabG1.test.ts`）**：`arenaConditionLines()` 只豁免

### 4. 关键设计
